# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NETLab / QoSLab — a browser-based Cisco IOS lab simulator for university networking students. Static HTML/CSS/JS frontend (no build step, no framework) plus a small FastAPI backend that proxies an AI tutor to OpenRouter. Content is Thai-first with embedded English networking terminology.

## Design Context

This project has `PRODUCT.md` and `DESIGN.md` at the project root — read them before any UI/design work.

- **PRODUCT.md**: register (`product`), users (university networking-course students), purpose (build real Cisco IOS command muscle memory), brand personality (precise, patient, no-nonsense), anti-references (no gamified LMS look), accessibility (WCAG AA).
- **DESIGN.md**: the visual system — "Rack & Instrument," black-and-blue dark theme / pure-white light theme. One accent hue (Signal Blue) for all interactivity, semantic status colors at genuinely distinct hues (green/amber/red/periwinkle), flat-by-default elevation with shadows reserved for overlays only, monospace for anything CLI-real, a shared type/spacing scale across all 5 pages.
- `.impeccable/design.json` is the machine-readable sidecar (tonal ramps, component snippets) consumed by the `$impeccable live` panel.

## Running locally

No build tooling — pages are served as static files and the backend runs directly with uvicorn.

```bash
# frontend (static files) — serves index.html, labs.html, etc. on :5500
python -m http.server 5500

# backend (AI tutor + progress API) — needs fastapi, uvicorn, httpx, python-dotenv, pydantic, google-auth
python -m uvicorn main:app --host 0.0.0.0 --port 8000
```

`.claude/launch.json` defines both as preview-tool configs (`static-preview`, `backend`) — prefer starting them through the preview tool rather than raw Bash so console/network/log inspection works.

Backend config lives in `.env`: `OPENROUTER_API_KEY`, the three `MODEL_*` names, `ALLOWED_ORIGINS`, `GOOGLE_CLIENT_ID`, `ALLOWED_EMAIL_DOMAIN`, and `SECRET_KEY` — which `session.py` needs to sign session tokens and refuses to run without, so login dies with a `RuntimeError` if it is missing. Each deployment generates its own `SECRET_KEY`; changing it logs everyone out, since tokens signed with the old one stop verifying. `main.py` loads `/opt/qoslab/.env` first (the prod path, still named after the old project name) then falls back to the local `.env` next to it.

The database is `netlab.db`, created on first run next to `main.py` and gitignored along with `.env` and `backups/` — it holds real student names, emails, quiz scores and AI chat transcripts. `backup_db.py` snapshots it through sqlite3's backup API rather than copying the file, because WAL mode leaves recently-committed data in the `-wal` sidecar. There is no test suite or linter configured in this repo.

## Architecture

**Pages** (each is a self-contained `.html` with inline `<style>` and a bottom `<script>` — no shared JS bundler):
- `index.html` — home page + a tabbed quick-reference panel (static routing, subnetting, dynamic routing protocols, DHCP) driven by `selectTopic()`/URL hash, no backend calls.
- `labs.html` — lab picker / roadmap linking to `course.html` and individual lab pages.
- `course.html` — course/module overview.
- `lab5.html` — the actual lab simulator: a fake Cisco IOS terminal (`runCmd()`, prompt/mode state machine in `APP`), a step checklist (`STEPS` array with expected commands + hints), an SVG topology diagram (`renderTopology()`), and an AI chat sidebar that calls the backend. Two `STEPS` entry shapes skip the terminal entirely and are driven by clicking a PC icon on the topology instead: `type:'pcconfig'` (`expected:{ip,mask,gateway}`) opens the IP-configuration popup, and `type:'pcping'` (`{router:'PC-A', target:{ip, label, ttl?}}`, `ttl` defaults to 125) opens a simulated Windows Command Prompt (`openPcModal()` dispatches to whichever popup is relevant; `findPcStep()`/`findPcPingStep()` locate a PC's step of each type) where the student types a real `ping <ip>` and sees authentic Windows-style output. Because that final step happens *inside* the PC window, `completeLab()` must close `#pcModalBackdrop` before showing the summary, and `.lab-complete` sits at `z-index:80` (above the PC backdrop's 50) — otherwise the summary renders underneath the Command Prompt and none of its buttons can be clicked. Every lab's final connectivity check is a `pcping` step — PC-to-PC, not router-to-PC — since that's how an end user actually verifies reachability; a lab with more than 2 router hops should keep the default `ttl` (125 assumes 3 hops), overriding it only when the topology's hop count differs (lab4's 2-router topology sets `ttl:126`).
- `lab1.html` / `lab2.html` / `lab3.html` — the three theory labs, which have no Cisco terminal at all. They share a lesson/checkpoint engine (`renderStep()` dispatches on `s.type`) and add one interactive engine each: `type:'wireorder'` (lab2, click-to-place UTP wire colors against T568A/T568B) and `type:'calc'` (lab3, per-field subnet-math validation). Two step types hold several questions at once and share one renderer: `type:'quiz'` is the gate between sections (three questions, the first being the section's original checkpoint), and `type:'review'` is the single end-of-chapter wrap-up. Both are drawn by `renderReview()`, which stacks every item on one page with ids namespaced per item index (`rvopt_K_N`, `rvddt_K_N`, `rvpin_K_N`, `rvcalc_K_key`) and grades them together in `submitReview()`; correct items lock, wrong ones clear so they can be retried. Items are ordinary step objects (mcq, dragdrop, wireorder or calc) plus a `topic` tag.

The wrap-up does not carry fixed questions: it sets `fromQuizzes:true` and holds a `pool[]`, and `rvDraw()` gathers that pool plus every `type:'quiz'` item in the chapter, picks **one question at random per `topic`**, and shuffles the order — so a retake is a real retest rather than a memory check (`resetLab()` clears `drawn` to force a fresh draw). Adding a question anywhere therefore widens the wrap-up pool automatically: give it the right `topic` and append it to a quiz's `items[]` or the review's `pool[]` — never add another step. Anything reading the question count must go through `rvCount()`, since `items` does not exist until the draw happens. `type:'lesson'` entries carry `body` (HTML prose) plus optional `fig` (an inline `<svg viewBox="0 0 600 H">` string) and `figCap` (one-line caption under it) — figures are what keep these text-only pages from reading as empty, so **a new lesson step should ship with one unless the idea is genuinely non-visual**. Draw them with the `.f-*` class kit defined in each lab's `<style>` (`.f-box`/`.f-box-a`/`.f-box-g`/`.f-box-p`/`.f-box-am`, `.f-ln`/`.f-ln-a`/`.f-ln-d`, `.f-t`/`.f-tb`/`.f-ts`/`.f-tm`/`.f-ta`/`.f-tg`) rather than hardcoded fills, so both themes work without a re-render hook — the one exception is real-world cable colors in lab2, which are fixed hex by nature. A correct answer never auto-advances: `showNextBtn()` replaces the check button with an explicit "ถัดไป →" so the student actually reads the explanation first. Any step already in `APP.stepsDone` reopens in **review mode**: `renderStep()` wraps `renderStepBase()` and calls `applyReviewMode()`, which reveals that step's answer (marks the correct option and shows the explanation, fills the T568 pins, fills the subnet fields read-only — the per-engine part lives in each lab's own `REVIEW_EXTRA()`) and swaps the action row for prev/next navigation. `APP.maxStep` is the furthest step unlocked; `goToStep()` refuses anything beyond it and only steps within it get a clickable sidebar row, so review never doubles as a way to skip ahead. Keep `APP.maxStep` in sync anywhere `APP.step` is assigned outside `advanceStep()` (restoring saved progress, `resetLab()`). Review is also blocked *while a test is open*: `isLockedInTest()` is true on any non-lesson step not yet in `stepsDone`, and `goToStep()` refuses then too — otherwise a student could click back into the lesson that hands them the answer.

Four rules came out of the course review and apply to any new theory content:
  1. **Lesson bodies carry the reasoning, not a summary.** A bullet list of definitions is not enough — each lesson runs roughly 800-1,200 characters and includes why the idea exists, concrete numbers, the mistake students actually make, and where it resurfaces in Lab 4-11.
  2. **Distractors must be defensible.** No joke options ("เพื่อความสวยงาม", "ใช้กับ Fiber เท่านั้น"), and never put the reasoning inside the option text (an option reading "…แต่ไม่ประหยัดที่สุด" answers itself). Vary `ans` across 0-3 as well — every correct answer in lab2 once sat at index 1, which is guessable on its own.
  3. **An exercise never reuses the worked example's numbers.** The lesson walks through one address, the exercise must use a different one, or the student is copying rather than calculating.
  4. **Figures are checked for collisions, not eyeballed.** Text nodes are laid out in fixed viewBox coordinates, so a type-scale change can silently make labels overlap. Walk every `fig` and compare each `<text>` `getBBox()` against the others and against the viewBox before considering figure work done.
- `dashboard.html` — student progress view (currently static/mock data; no `localStorage` or backend persistence wired up yet).
- `*.backup.html` / `*.bak` files are point-in-time snapshots, not live pages — don't edit them expecting effect.

**Shared assets:**
- `styles/tokens.css` — all design tokens (colors, spacing, type scale) as CSS custom properties, keyed off `[data-theme="light"|dark]`. Any new UI must use these tokens, not hardcoded values.
- `styles/shared.css` — shared component styles (topbar, nav, buttons, cards) reused across pages.
- `scripts/theme.js` — theme toggle + nav/settings dropdown behavior, shared via `<script src>` on every page. Defines global `toggleTheme()`, `toggleNav()`, `toggleSettings()`; pages without `#navLinks`/`#settingsMenu` just no-op. Pages needing a post-theme-change hook (e.g. `lab5.html`'s SVG topology) define `window.onThemeChange`.
- `scripts/cisco-patterns.js` — shared Cisco IOS command-abbreviation pattern library, included via `<script src>` on every `labN.html` (right after `theme.js`, before the lab's own inline `<script>`). Defines the generic `abbr(word, minLen)` builder plus every command-pattern function/constant the labs' `STEPS[].commands[].pat` regexes reference (`ENABLE_PAT`, `ifpat`, `ipAddrPat`, `hostnamePat`, `routerOspfPat`, `neighborRemoteAsPat`, `writeMemPat`, `EXIT_PAT`, etc.), plus `BASE_MODE_KEYWORDS`/`modeKeywords(configRouterWords)` — the per-mode word lists `isGibberish()`/`tabComplete()` use in every lab's terminal — one definition reused by every lab instead of duplicated per file. **Any new lab (remaining topics this semester, or a future semester-2 course) should add its command patterns here** — as a parameterized function if the lab has lab-specific literals (process IDs, AS numbers, metrics), or reuse an existing one — rather than hand-rolling a new local regex, so abbreviation coverage and future fixes stay centralized. A regression check exists at the point this was introduced: every `STEPS[].answer` across all labs must still `.test()` true against its own command chain after any change here — verify before committing, and verify the *abbreviated* forms too. **Every keyword must go through `abbr(word, minLen)`** — hand-rolled nested groups caused a real bug where `int` and `gi` passed but `inter` and `gig` failed, because the optionals were nested per syllable instead of per character. `minLen` is the shortest prefix that is genuinely unambiguous *in the mode that command is typed in*, matching real IOS: `no sh`, `in g0/0`, `ip ad`, `ho`, `tr`, `us`, `nei`, `red`, `no au` all work. Three keywords are deliberately long because IOS itself rejects the short form as ambiguous — `route` (vs `routing`), `router` (vs `route`/`routing`) and `domain-name` (vs `domain-lookup`/`domain-list`). Rejecting a valid abbreviation is worse than it looks: `isGibberish()` recognizes the keyword, so the input is scored as a wrong attempt rather than ignored, pushing the student toward the answer-reveal threshold for typing correct Cisco. The student-facing explanation of all this lives in `index.html` under the Quick Reference topic `abbr` — keep the two reference tables there in sync when a `minLen` changes. **Cache-busting:** every `<script src>` tag for this file carries a `?v=N` query string (currently `?v=3`) — Python's `http.server` sends no strong cache-control headers, so browsers can silently keep serving an old cached copy after an edit here, breaking every lab's terminal with a `ReferenceError` partway through init (symptom: typing in the terminal does nothing). **Bump `?v=N` by 1 across all 8 `labN.html` files whenever this file's content changes** — the query string is a plain cache key, not a real version scheme, so any new distinct value works. The same applies to the other shared assets: `tokens.css`, `shared.css`, `theme.js` and `auth.js` each carry `?v=N` (currently `?v=1`) on all 17 live pages, so a token or theme edit actually reaches a returning student — bump those the same way, and leave `*.backup-*.html` snapshots untouched when doing a sweep like this.
- `assets/topic-images/` — illustration images for reference topics.

**Backend:** FastAPI across four files — `main.py` (HTTP), `db.py` (SQLite), `session.py` (session tokens), `backup_db.py` (a cron/Task Scheduler entry point, not imported by the app). Endpoints: `/chat`, `/auth/google`, `/progress` (POST + GET), `/quiz-score`, `/health`, `/models`.

`db.py` owns `netlab.db` — four tables matching the four things §2.4.9 of the ทก.01 proposal says SQLite stores: `users`, `progress` (+ `activity` for the dashboard's per-day graph), `quiz_attempts`, `ai_chat_logs`. `course_id` disambiguates `lab_id` across courses (`netlab1` this term, `netlab2` reserved for Lab II), so it is part of every primary key. `init_db()` runs on import and holds two idempotent migrations — one brings an older `progress` table up to the current PK and CHECK constraints, the other stamps the UTC offset onto rows written before the module became timezone-aware. Timestamps are UTC; only `activity.day` is bucketed by the Bangkok calendar day, because a UTC date files late-night practice under the previous day. **Not yet in the schema, and needed for semester 2:** `difficulty` (scope item 1.2 wants Basic/Medium/Hard, and it has to join the `progress` PK or a retry at another level overwrites the first), `hints_used` (the difficulty levels cap hint count, which `wrong_count` cannot stand in for), and `classrooms`/`enrollments` (scope item 2.2).

`session.py` issues and verifies HMAC-signed opaque tokens (`SECRET_KEY` in `.env`, 7-day TTL matching `auth.js`'s `AUTH_SESSION_DAYS`). **`/progress` and `/quiz-score` derive `studentId` from the token and no longer trust one sent by the page**, so any new call that reads or writes a student's data must send `getToken()` from `auth.js` — in the JSON body for POSTs, as `?token=` for GETs. Guests have no token: `saveQuizScore()` returns early for them, and `/chat` logs their turn with a NULL `student_id` rather than refusing it. Because `quiz_attempts`/`ai_chat_logs` FK-reference `users`, a token that outlives its database (fresh deploy, restored backup, wiped dev DB) names a student the DB has never seen — `/quiz-score` answers 401 there, not 500, so the frontend sends them back through sign-in.

`/chat` itself:
- `detect_task()` classifies each request as `hint` / `explain` / `chat` from keywords.
- `extract_wrong_count()` reads a "wrong X times" marker the frontend embeds in the `system` prompt.
- `inject_hint_guard()` appends a rule to the system prompt so the tutor withholds full answers until the student has failed enough times — this rationing is a deliberate product behavior (see PRODUCT.md "Earn the answer"), not a bug to relax.
- `select_model()` routes to `MODEL_FAST` (hints), `MODEL_FALLBACK` (≥4 wrong attempts), or `MODEL_DEFAULT` (everything else) — three OpenRouter models configured via `.env`.
- On timeout, `/chat` retries once against `MODEL_FAST` before failing.
- Frontend pages call it via `API_BASE`, computed per-page as `http://localhost:8000` on localhost or `http://<host>/api` otherwise (see `lab5.html`) — keep this convention if adding new AI-calling pages.
