# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NETLab — a browser-based Cisco IOS lab simulator for university networking students. Static HTML/CSS/JS frontend (no build step, no framework) plus a small FastAPI backend that proxies an AI tutor to OpenRouter. Content is Thai-first with embedded English networking terminology.

## Design Context

This project has `PRODUCT.md` and `DESIGN.md` at the project root — read them before any UI/design work.

- **PRODUCT.md**: register (`product`), users (university networking-course students), purpose (build real Cisco IOS command muscle memory), brand personality (precise, patient, no-nonsense), anti-references (no gamified LMS look), accessibility (WCAG AA).
- **DESIGN.md**: the visual system — "Rack & Instrument," black-and-blue dark theme / pure-white light theme. One accent hue (Signal Blue) for all interactivity, semantic status colors at genuinely distinct hues (green/amber/red/periwinkle), flat-by-default elevation with shadows reserved for overlays only, monospace for anything CLI-real, a shared type/spacing scale across every page.
- `.impeccable/design.json` is the machine-readable sidecar (tonal ramps, component snippets) consumed by the `$impeccable live` panel.

## Running locally

No build tooling — pages are served as static files and the backend runs directly with uvicorn.

**Everything web-servable lives under `public/`** (all page HTML, `styles/`, `scripts/`, `assets/`, `labnetwork1/`). Backend code (`main.py`, `db.py`, `session.py`, `backup_db.py`), `.env`, and `netlab.db` stay at the project root, *outside* the static file root — this is deliberate: `python -m http.server`/a naive nginx `root` serves every file under its root verbatim, and this project's `.env`/database/source once sat directly inside the served directory and were downloadable by anyone who could reach the site (found and fixed 2026-09-27). Never add a new backend/data file under `public/`, and never point the static server's root at the project root instead of `public/`.

```bash
# frontend (static files) — serves public/index.html, public/labs.html, etc. on :5500
python -m http.server 5500 --directory public

# backend (AI tutor proxy) — needs fastapi, uvicorn, httpx, python-dotenv, pydantic
python -m uvicorn main:app --host 0.0.0.0 --port 8000
```

`.claude/launch.json` defines both as preview-tool configs (`static-preview`, `backend`) — prefer starting them through the preview tool rather than raw Bash so console/network/log inspection works.

Backend config lives in `.env` (OpenRouter API key + model names + `ALLOWED_ORIGINS`, plus `SECRET_KEY` and `GOOGLE_CLIENT_ID`, without which login fails). `main.py` first tries `/opt/qoslab/.env`, a legacy path that the planned deployment does not use. It then falls back to the `.env` next to `main.py`. Python dependencies are pinned in `requirements.txt`. There is no test suite configured in this repo.

## Deployment — not deployed yet

As of 2026-10-03 NETLab has **never been deployed**. Everything so far runs only on the developer's machine, and no production server, production database or student data exists yet. The target is the university's (KMUTNB) server, set up from scratch. `deploy/` holds everything for that:
- `DEPLOY.md` is the step-by-step guide, in Thai.
- `nginx-netlab.conf` and `netlab-backend.service` are the server configs.
- `env.example` lists the `.env` keys.

The layout is `/opt/netlab`: nginx serves `frontend/dist/` and proxies `/api/` to uvicorn on `127.0.0.1:8000`. Google Sign-In needs a real https domain, which must be added as an authorized JavaScript origin of the OAuth client. The server starts with an empty `netlab.db`. Never upload the local one, which holds test data. Update `deploy/` whenever the server layout, `.env` keys or nginx needs change.

## React frontend (`frontend/`) — the frontend to deploy

All 17 pages have been rewritten as React 19 + TypeScript on **Vite**, in `frontend/`, and the built `frontend/dist/` is what gets deployed. **New UI and content work goes in `frontend/` only.** `public/`, the original vanilla pages, is legacy reference and is no longer updated. `public/เอกสาร_โครงสร้าง_DB.html` remains the schema doc but is not part of the build. HTML is served `no-cache` and the hashed bundles are cached for a year (see `deploy/nginx-netlab.conf`): each HTML file names its hashed bundles, so a stale cached HTML file would keep loading the previous release. The `frontend-dist` launch config serves `frontend/dist` on :4173 for checking a build before it ships.

```bash
npm --prefix frontend run dev        # :5173, proxies /api -> :8000 (launch config "frontend-dev")
npm --prefix frontend run build      # -> frontend/dist, one HTML per page at the same paths as public/
npx --prefix frontend tsc --noEmit -p frontend/tsconfig.app.json   # type-check
```

- **Multi-page build, not an SPA** — every page in `vite.config.ts` `rollupOptions.input` keeps its original URL (`/labs.html`, `/labnetwork1/lab05-static-route/lab5.html`, …) so bookmarks, course/dashboard links and the nginx static-root model keep working. Adding a page means adding an HTML entry there too.
- `src/pages/<page>/` — the six top-level pages. `src/labs/labNN/` — one folder per lab: its data file plus a thin page component.
- `src/components/configlab/` — the **Config Lab engine** (Lab 4-11): `ConfigLab.tsx` takes STEPS/NODES/LINKS/PRETEST and per-lab text as props; each `labNData.ts` is that lab's original data. The terminal state machine lives in a ref (`appRef`) mutated then re-rendered, because `runCmd` reads-after-writes within one keystroke. `initialPrompt`, `configRouterWords`, `nextLabLabel` cover the per-lab differences.
- `src/components/theorylab/` — the **Theory Lab engine** (Lab 1-3): lesson / checkpoint / calc / wireorder / quiz / review views; same review-draw, test-lock and review-mode rules as described under Pages below. `labNSteps.ts` was **copied verbatim from the original `STEPS` literal by script** — never retype lesson HTML or figures by hand.
- `src/components/lab/` — topbar and AI-health hook shared by both engines. `src/lib/ciscoPatterns.ts` is the port of `scripts/cisco-patterns.js` (same `abbr()` rules); `src/lib/api.ts` is the typed client for every endpoint. Vite content-hashes assets, so the `?v=N` cache-busting rule does not apply here.
- `/chat` calls from the new frontend send `token` + `labId`, so `ai_chat_logs` rows are attributed (the vanilla pages never sent them).
- A 401 from `/progress` or `/quiz-score` clears the stored session and redirects to `login.html` (`endSessionIfRejected()` in `api.ts`), and a stored non-guest session with no token is treated as signed out. Without this a rejected token made every save fail silently.
- **Accessibility conventions, applied across the whole frontend 2026-10-03.** Every page renders one `<h1>` (the lab engines put a visually hidden one in `LabTopbar`, since a lab swaps between pre-test, lesson and summary and no visible element serves as the heading for the session), a `<header>`, a `<main id="main" tabIndex={-1}>` and a skip link as its first focusable element. An element that behaves as a button without being one spreads `clickable()` from `src/lib/clickable.ts`, which supplies role, a tab stop and Enter/Space activation; passing a falsy handler returns `{}`, which is what keeps conditionally-clickable things (sidebar step rows, the topology's PC icons) from becoming tab stops while inert. Dismiss surfaces — the modal, mobile and reference backdrops — are deliberately excluded, since the dialog each covers has its own cancel button. `shared.css` carries `prefers-reduced-motion`, `.skip-link`, `.sr-only` and the `[data-kbd]` focus ring, and `Providers.tsx` imports it, so one block reaches all 17 pages. Before this pass no page had a heading or a landmark and 24 controls were unreachable by keyboard, two of which blocked finishing a lab: pre-test options and the PC icon every lab's final step depends on.
- **Never let a placeholder be the answer.** The PC dialog's Subnet Mask placeholder used to read `255.255.255.0`, which every lab expects. Placeholders there now show the shape of an address and a line points at the task box for the real values (PRODUCT.md, "Earn the answer").
- **CSS gotcha:** never put `*/` inside a CSS comment (e.g. a path like `lab0N-*/labN.html`). It ends the comment early; dev silently drops the next rule and the production build fails.

## Architecture

**Pages** (each is a self-contained `.html` with inline `<style>` and a bottom `<script>` — no shared JS bundler; all served from `public/`, see "Running locally" above):
- `index.html` — home page + a tabbed quick-reference panel (static routing, subnetting, dynamic routing protocols, DHCP) driven by `selectTopic()`/URL hash, no backend calls.
- `login.html` — Google Sign-In (`@email.kmutnb.ac.th` only) via `scripts/auth.js`'s `handleGoogleCredential()`, which posts the ID token to `POST /auth/google` and stores the returned session token + profile in `localStorage`. Also offers a LAN-only guest mode (`signInAsGuest()`, gated by `isLanHost()`) for classmates on the same Wi-Fi who can't complete Google OAuth against a raw IP — a guest has no `studentId`, so `saveProgress()` on every lab page silently no-ops for them.
- `profile.html` — read-only profile view (name/email/studentId from the signed-in session) + logout.
- `labs.html` — lab picker / roadmap linking to `course.html`; the "Network Engineering Laboratory I" card's done-count/percentage comes from `loadCatalogProgress()` (`GET /progress/{studentId}?token=...&course_id=netlab1`) — not hardcoded (fixed 2026-09-27; it used to be a static "36%").
- `course.html` — per-lab roadmap (done/active/locked) for all 11 labs, built from the same `/progress` response via `buildLabsFromProgress()`. Its `LAB_META`/`LAB_BUILT` arrays are duplicated in `dashboard.html` — edit both when adding/renaming a lab.
- `dashboard.html` — student progress view: per-lab status table + a weekly practice-hours graph, both from `GET /progress/{studentId}?token=...` (`labs` + `weeklyActivity`). Real data, not mock, despite what older comments here used to say.
- `public/labnetwork1/lab0N-topic/labN.html` (N = 1–11) — the actual lab pages for **Network Engineering Laboratory I**:
  - **Lab 1–3** (`lab01-course-intro`, `lab02-cable-termination`, `lab03-ip-subnetting`) are the theory labs, which have no Cisco terminal at all. They share a lesson/checkpoint engine (`renderStep()` dispatches on `s.type`) and add one interactive engine each: `type:'wireorder'` (lab2, click-to-place UTP wire colors against T568A/T568B) and `type:'calc'` (lab3, per-field subnet-math validation). Two step types hold several questions at once and share one renderer: `type:'quiz'` is the gate between sections (three questions, the first being the section's original checkpoint), and `type:'review'` is the single end-of-chapter wrap-up. Both are drawn by `renderReview()`, which stacks every item on one page with ids namespaced per item index (`rvopt_K_N`, `rvddt_K_N`, `rvpin_K_N`, `rvcalc_K_key`) and grades them together in `submitReview()`; correct items lock, wrong ones clear so they can be retried. Items are ordinary step objects (mcq, dragdrop, wireorder or calc) plus a `topic` tag. `submitReview()` also POSTs every attempt (pass or fail, `quiz_key` = `s.type+'_'+s.id`) to `/quiz-score` via `saveQuizScore()`.
  - **Lab 4–11** (`lab04-basic-configuration` through `lab11-bgp`) are the Config Lab pages: a fake Cisco IOS terminal (`runCmd()`, prompt/mode state machine in `APP`), a step checklist (`STEPS` array with expected commands + hints), an SVG topology diagram (`renderTopology()`), and an AI chat sidebar that calls the backend. A `PRETEST[]`/`checkPretest()` quiz gates entry to the terminal and reports its score to `/quiz-score` via `savePretestScore()`. Two `STEPS` entry shapes skip the terminal entirely and are driven by clicking a PC icon on the topology instead: `type:'pcconfig'` (`expected:{ip,mask,gateway}`) opens the IP-configuration popup, and `type:'pcping'` (`{router:'PC-A', target:{ip, label, ttl?}}`, `ttl` defaults to 125) opens a simulated Windows Command Prompt (`openPcModal()` dispatches to whichever popup is relevant; `findPcStep()`/`findPcPingStep()` locate a PC's step of each type) where the student types a real `ping <ip>` and sees authentic Windows-style output. Because that final step happens *inside* the PC window, `completeLab()` must close `#pcModalBackdrop` before showing the summary, and `.lab-complete` sits at `z-index:80` (above the PC backdrop's 50) — otherwise the summary renders underneath the Command Prompt and none of its buttons can be clicked. Every lab's final connectivity check is a `pcping` step — PC-to-PC, not router-to-PC — since that's how an end user actually verifies reachability; a lab with more than 2 router hops should keep the default `ttl` (125 assumes 3 hops), overriding it only when the topology's hop count differs (lab4's 2-router topology sets `ttl:126`).
  - Every lab's `saveProgress()`/restore-progress fetch must include `token:getToken()` (POST body field) or `?token=` (GET query param) — the backend derives the real student ID from this token and rejects a mismatched `studentId`, so a page that forgets it gets silent 401s (progress just stops saving, no visible error).

Project documents (ทก01 proposal and drafts, `Project.rar`) went to `E:\Project_docs\` and screenshots to `E:\Project_docs\screenshots\`. Don't recreate them here.

The wrap-up does not carry fixed questions: it sets `fromQuizzes:true` and holds a `pool[]`, and `rvDraw()` gathers that pool plus every `type:'quiz'` item in the chapter, picks **one question at random per `topic`**, and shuffles the order — so a retake is a real retest rather than a memory check (`resetLab()` clears `drawn` to force a fresh draw). Adding a question anywhere therefore widens the wrap-up pool automatically: give it the right `topic` and append it to a quiz's `items[]` or the review's `pool[]` — never add another step. Anything reading the question count must go through `rvCount()`, since `items` does not exist until the draw happens. `type:'lesson'` entries carry `body` (HTML prose) plus optional `fig` (an inline `<svg viewBox="0 0 600 H">` string) and `figCap` (one-line caption under it) — figures are what keep these text-only pages from reading as empty, so **a new lesson step should ship with one unless the idea is genuinely non-visual**. Draw them with the `.f-*` class kit defined in each lab's `<style>` (`.f-box`/`.f-box-a`/`.f-box-g`/`.f-box-p`/`.f-box-am`, `.f-ln`/`.f-ln-a`/`.f-ln-d`, `.f-t`/`.f-tb`/`.f-ts`/`.f-tm`/`.f-ta`/`.f-tg`) rather than hardcoded fills, so both themes work without a re-render hook — the one exception is real-world cable colors in lab2, which are fixed hex by nature. A correct answer never auto-advances: `showNextBtn()` replaces the check button with an explicit "ถัดไป →" so the student actually reads the explanation first. Any step already in `APP.stepsDone` reopens in **review mode**: `renderStep()` wraps `renderStepBase()` and calls `applyReviewMode()`, which reveals that step's answer (marks the correct option and shows the explanation, fills the T568 pins, fills the subnet fields read-only — the per-engine part lives in each lab's own `REVIEW_EXTRA()`) and swaps the action row for prev/next navigation. `APP.maxStep` is the furthest step unlocked; `goToStep()` refuses anything beyond it and only steps within it get a clickable sidebar row, so review never doubles as a way to skip ahead. Keep `APP.maxStep` in sync anywhere `APP.step` is assigned outside `advanceStep()` (restoring saved progress, `resetLab()`). Review is also blocked *while a test is open*: `isLockedInTest()` is true on any non-lesson step not yet in `stepsDone`, and `goToStep()` refuses then too — otherwise a student could click back into the lesson that hands them the answer.

Four rules came out of the course review and apply to any new theory content:
  1. **Lesson bodies carry the reasoning, not a summary.** A bullet list of definitions is not enough — each lesson runs roughly 800-1,200 characters and includes why the idea exists, concrete numbers, the mistake students actually make, and where it resurfaces in Lab 4-11.
  2. **Distractors must be defensible.** No joke options ("เพื่อความสวยงาม", "ใช้กับ Fiber เท่านั้น"), and never put the reasoning inside the option text (an option reading "…แต่ไม่ประหยัดที่สุด" answers itself). Vary `ans` across 0-3 as well — every correct answer in lab2 once sat at index 1, which is guessable on its own.
  3. **An exercise never reuses the worked example's numbers.** The lesson walks through one address, the exercise must use a different one, or the student is copying rather than calculating.
  4. **Figures are checked for collisions, not eyeballed.** Text nodes are laid out in fixed viewBox coordinates, so a type-scale change can silently make labels overlap. Walk every `fig` and compare each `<text>` `getBBox()` against the others and against the viewBox before considering figure work done.
- `*.backup.html` / `*.bak` / `*.backup-<timestamp>.html` files are point-in-time snapshots, not live pages — don't edit them expecting effect.

**Shared assets:**
- `styles/tokens.css` — all design tokens (colors, spacing, type scale) as CSS custom properties, keyed off `[data-theme="light"|dark]`. Any new UI must use these tokens, not hardcoded values.
- `styles/shared.css` — shared component styles (topbar, nav, buttons, cards) reused across pages.
- `scripts/theme.js` — theme toggle + nav/settings dropdown behavior, shared via `<script src>` on every page. Defines global `toggleTheme()`, `toggleNav()`, `toggleSettings()`; pages without `#navLinks`/`#settingsMenu` just no-op. Pages needing a post-theme-change hook (e.g. `lab5.html`'s SVG topology) define `window.onThemeChange`.
- `scripts/auth.js` — Google Sign-In + client-side session gate, shared via `<script src>` on every page. Defines `getProfile()`/`getToken()` (read the signed-in student's profile/session token from `localStorage`, both `null` if expired/absent), `requireAuth()` (redirect to `login.html` if not signed in), `logout()`, and `handleGoogleCredential()` (posts the Google ID token to `POST /auth/google`, stores `{profile, token, exp}` on success). Every backend call that touches a specific student's data must send `getToken()` alongside the request — see `/progress`/`/quiz-score` under Backend below.
- `scripts/cisco-patterns.js` — shared Cisco IOS command-abbreviation pattern library, included via `<script src>` on every `labN.html` (right after `theme.js`, before the lab's own inline `<script>`). Defines the generic `abbr(word, minLen)` builder plus every command-pattern function/constant the labs' `STEPS[].commands[].pat` regexes reference (`ENABLE_PAT`, `ifpat`, `ipAddrPat`, `hostnamePat`, `routerOspfPat`, `neighborRemoteAsPat`, `writeMemPat`, `EXIT_PAT`, etc.), plus `BASE_MODE_KEYWORDS`/`modeKeywords(configRouterWords)` — the per-mode word lists `isGibberish()`/`tabComplete()` use in every lab's terminal — one definition reused by every lab instead of duplicated per file. **Any new lab (remaining topics this semester, or a future semester-2 course) should add its command patterns here** — as a parameterized function if the lab has lab-specific literals (process IDs, AS numbers, metrics), or reuse an existing one — rather than hand-rolling a new local regex, so abbreviation coverage and future fixes stay centralized. A regression check exists at the point this was introduced: every `STEPS[].answer` across all labs must still `.test()` true against its own command chain after any change here — verify before committing, and verify the *abbreviated* forms too. **Every keyword must go through `abbr(word, minLen)`** — hand-rolled nested groups caused a real bug where `int` and `gi` passed but `inter` and `gig` failed, because the optionals were nested per syllable instead of per character. `minLen` is the shortest prefix that is genuinely unambiguous *in the mode that command is typed in*, matching real IOS: `no sh`, `in g0/0`, `ip ad`, `ho`, `tr`, `us`, `nei`, `red`, `no au` all work. Three keywords are deliberately long because IOS itself rejects the short form as ambiguous — `route` (vs `routing`), `router` (vs `route`/`routing`) and `domain-name` (vs `domain-lookup`/`domain-list`). Rejecting a valid abbreviation is worse than it looks: `isGibberish()` recognizes the keyword, so the input is scored as a wrong attempt rather than ignored, pushing the student toward the answer-reveal threshold for typing correct Cisco. The student-facing explanation of all this lives in `index.html` under the Quick Reference topic `abbr` — keep the two reference tables there in sync when a `minLen` changes. **Cache-busting:** every `<script src>` tag for this file carries a `?v=N` query string (currently `?v=6`) — Python's `http.server` sends no strong cache-control headers, so browsers can silently keep serving an old cached copy after an edit here, breaking every lab's terminal with a `ReferenceError` partway through init (symptom: typing in the terminal does nothing). **Bump `?v=N` by 1 across all 8 `labN.html` files whenever this file's content changes** — the query string is a plain cache key, not a real version scheme, so any new distinct value works. The same applies to the other shared assets: `tokens.css` (currently `?v=3`), `shared.css` (`?v=2`), `theme.js` (`?v=2`) and `auth.js` (`?v=3`) each carry their own `?v=N` on all 17 live pages, so a token or theme edit actually reaches a returning student — bump those the same way, and leave `*.backup-*.html` snapshots untouched when doing a sweep like this.
- `assets/topic-images/` — illustration images for reference topics.

**Backend (`main.py` + `db.py` + `session.py`):** FastAPI app backed by a single-file SQLite database (`netlab.db`, at the project root — see "Running locally" above for why it's *not* under `public/`). Five tables: `users`, `progress`, `activity`, `quiz_attempts`, `ai_chat_logs` — full column-level schema and API request/response shapes are documented in `public/เอกสาร_โครงสร้าง_DB.html` (keep it in sync with `db.py` when the schema changes). `progress` is keyed `(student_id, course_id, lab_id, difficulty)` — `difficulty` is **in the primary key**, not beside it, because the same student retrying a lab at another level is a separate attempt; keyed without it the second attempt UPDATEs over the first and leaves a row claiming 5 of 30 steps while still flagged completed. It is not switched on: `DIFFICULTY` in `api.ts` is pinned to `'basic'`, so semester 2's level picker (scope item 1.2) changes one line rather than every call site. `hints_used` counts hint-button presses and arrives as `hintsDelta`, a delta like `wrongDelta`, because a student can press hint and still answer correctly first try — `wrong_count` cannot stand in for the hint quota the levels impose; only the config labs count it. **Two things to handle when the picker ships:** `Dashboard.tsx` keeps one row per `lab_id` and will silently show whichever level sorts last, and `quiz_attempts` has no `difficulty` column. `db.py` runs its own idempotent migrations on every `init_db()` call (safe to run on every startup; backfills/clamps legacy rows rather than dropping data) and opens the connection in WAL mode with `CHECK` constraints on every numeric column.

Session auth (`session.py`): `POST /auth/google` issues a stdlib-only HMAC-signed token (`issue_token`/`verify_token`, no JWT dependency) after verifying the Google ID token (`clock_skew_in_seconds=10` — google-auth defaults to **0**, which rejects a valid token on nothing more than 1 second of clock drift between this server and Google's) and restricting to `ALLOWED_EMAIL_DOMAIN`. Every endpoint that reads or writes a specific student's data (`/progress`, `/quiz-score`) requires this token and derives the real `student_id` from it — **never** trust a client-supplied `studentId`/path param alone; a request whose token doesn't match the `studentId` it claims gets a 403. (This used to be a real, exploitable hole — any client could read or forge any student's progress — closed 2026-09-27.) The token travels in the request **body** (POST) or a **query param** (GET), not an `Authorization` header, because `saveProgress()` fires via both a normal `fetch()` and `navigator.sendBeacon()` on `pagehide`, and `sendBeacon` can't set custom headers.

Endpoints:
- `POST /auth/google` — see above; also upserts the student into `users` (`db.upsert_user`).
- `POST /progress` / `GET /progress/{student_id}` — read/write one lab's `steps_done`/`wrong_count`/`time_spent_sec`/`completed`, plus the `activity` table (daily practice-seconds, feeds the Dashboard's weekly graph). `wrongDelta`/`elapsedSec` are accumulated server-side (`db.upsert_progress` adds to the existing row), not overwritten. `activity.day` is a Thai-time (UTC+7, `db.LOCAL_TZ`) calendar day, so practice before 07:00 is not counted on the previous day's bar. Rows written before 2026-10-02 used UTC days. `require_student()` also returns 401 when the token's student has no `users` row, rather than letting the `quiz_attempts` foreign key raise a 500. The request models reject `stepsDone > totalSteps` and `score > maxScore` with a 422, and `/chat` input is size-capped (≤20 messages, 8,000 characters each, 20,000-character system prompt).
- `POST /quiz-score` — records one quiz/Pre-test attempt into `quiz_attempts` (`db.save_quiz_attempt`, `attempt_no` auto-increments per student+course+lab+`quiz_key`). Called by `checkPretest()` (Lab 4–11) and `submitReview()` (Lab 1–3, every quiz/review checkpoint, on both pass and fail — see Pages above).
- `POST /chat` — the AI tutor proxy. `detect_task()` classifies each request as `hint`/`explain`/`chat` from keywords; `extract_wrong_count()` reads a "wrong X times" marker the frontend embeds in the `system` prompt; `inject_hint_guard()` appends a rule so the tutor withholds full answers until the student has failed enough times — this rationing is a deliberate product behavior (see PRODUCT.md "Earn the answer"), not a bug to relax; `select_model()` routes to `MODEL_FAST` (hints), `MODEL_FALLBACK` (≥4 wrong attempts), or `MODEL_DEFAULT` (everything else) — three OpenRouter models configured via `.env`. `MODEL_FAST` was `deepseek/deepseek-v4-flash` until 6 Oct 2026: measured on the Lab 5 hint prompt it returned empty 8 times in 10 (the budget went on its internal reasoning), so every hint paid for a wasted round trip before falling through to `MODEL_DEFAULT` — about 9 seconds. It is now the same model as `MODEL_DEFAULT`, measured at 1.65 s (1.45–2.06) over 5 rounds with no fallback. It stays a separate key so the two can diverge again. **`call_openrouter()` returns `(content, answered_by)`** and both the response and `ai_chat_logs.model_used` carry the model that produced the words, not the one requested — returning only the text is what let the database attribute answers to a model that had answered nothing, and made any latency drawn from it describe the wrong model. On timeout, retries once against `MODEL_FAST` before failing. Every successful reply is logged to `ai_chat_logs` via `db.log_chat()` (student ID from the token if present, `None` for an unauthenticated guest — chat still works, just isn't attributed to anyone).
- `GET /health`, `GET /models` — status/model-list, unauthenticated.

Frontend pages call the backend via `API_BASE`, computed per-page as `http://localhost:8000` on localhost or `http://<host>/api` otherwise (see any `labN.html`) — keep this convention if adding new AI-calling pages.

`backup_db.py` is a standalone script, not an endpoint — run it daily via cron (prod) or Task Scheduler (local dev) to snapshot `netlab.db` into `backups/` using SQLite's backup API (safe under WAL mode, unlike a plain file copy); keeps the last 30 snapshots.
