เหตุผลการออกแบบ

1
SQLite ไฟล์เดียว ไม่ใช้ ORM — ใช้ sqlite3 มาตรฐานของ Python ตรงตามที่ระบุไว้ใน ทก.01 (§2.7.6) แม้ตอนนี้จะขยายเป็น 5 ตารางแล้ว ก็ยังไม่จำเป็นต้องเพิ่ม dependency ใหม่
2
wrong_count และ time_spent_sec เป็นค่า "บวกสะสม" ไม่ใช่ค่าล่าสุด — ทุกครั้งที่บันทึก backend จะบวกทับของเดิม ไม่เขียนทับ เพราะนักศึกษาอาจปิดหน้าเว็บแล้วกลับมาทำต่อหลายรอบ ต้องนับรวมทุกรอบ ไม่ใช่แค่รอบล่าสุด (ตอนนี้ถูกจำกัดด้วย CHECK ≥ 0 และ Pydantic Field(ge=0) กันค่าติดลบจากฝั่ง client ด้วย)
3
แยกตาราง activity ออกจาก progress — progress เก็บสถานะ "ล่าสุด" ต่อ Lab (แถวเดียวอัปเดตทับ) ส่วน activity ต้องเก็บ "ประวัติรายวัน" (แถวใหม่ทุกวัน) เพื่อวาดกราฟ Practice Hours ย้อนหลัง 7 วันในหน้า Dashboard ถ้ารวมสองอย่างในตารางเดียวจะคำนวณกราฟยากและข้อมูลซ้ำซ้อน
4
ส่งค่าตอนทำ Step สำเร็จ + ตอนออกจากหน้า (pagehide) — ไม่ส่งทุก keystroke เพื่อไม่ให้ยิง request ถี่เกินไป แต่กันเวลาหายถ้านักศึกษาปิดแท็บกลางคันโดยยังไม่ทำ Step สำเร็จ
5
session token แทนการเชื่อ studentId ตรงๆ — เดิม /progress รับ studentId จาก client โดยไม่ตรวจสอบเลย ใครก็แก้ค่าใน request แล้วปลอม/อ่านผลเรียนของคนอื่นได้ ตอนนี้ /auth/google ออก token ที่เซ็นด้วย HMAC (session.py, stdlib ล้วน ไม่เพิ่ม dependency) ทุก endpoint ที่แตะข้อมูลของนักศึกษาต้องแนบ token นี้ และ server ดึง studentId จาก token เองเสมอ ไม่ใช่จาก body/query ที่ client ส่งมา — ส่ง token ทาง body/query แทน Authorization header เพราะ saveProgress() ยิงทั้ง fetch() ปกติและ navigator.sendBeacon() ตอนปิดแท็บ ซึ่ง sendBeacon ตั้ง header เองไม่ได้
6
users / quiz_attempts / ai_chat_logs เพิ่มเข้ามาให้ตรงกับ ทก.01 §2.4.9 — เอกสารเสนอโครงงานระบุว่า SQLite เก็บ "ข้อมูลผู้ใช้งาน ผลคะแนนแบบทดสอบ และประวัติการโต้ตอบกับ AI Tutor" แต่ก่อนหน้านี้มีแค่ progress/activity เท่านั้น ตอนนี้ /auth/google upsert เข้า users, checkPretest() (Lab 4–11) และ submitReview() (Lab 1–3, ทุก quiz/review checkpoint — ยิงทั้งตอนผ่านและตอนยังไม่ผ่าน เพื่อเก็บจำนวนครั้งที่พยายามจริง) ยิงคะแนนเข้า quiz_attempts, และ /chat log ทุกบทสนทนาเข้า ai_chat_logs
