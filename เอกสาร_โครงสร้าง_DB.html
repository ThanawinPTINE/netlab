โครงสร้างฐานข้อมูล

NETLab — ระบบเรียนรู้เนื้อหาปฏิบัติการวิศวกรรมสารสนเทศและเครือข่ายแบบโต้ตอบด้วยปัญญาประดิษฐ์

ระบบจัดการฐานข้อมูล SQLite ไฟล์ netlab.db 5 ตาราง 41 คอลัมน์ โมดูลที่จัดการ db.py
เอกสารนี้สร้างจากสคีมาจริงของไฟล์ netlab.db โดยอ่านผ่านคำสั่ง PRAGMA ไม่ได้พิมพ์ด้วยมือ — ชื่อตาราง คอลัมน์ ชนิดข้อมูล และเงื่อนไขทั้งหมด จึงตรงกับฐานข้อมูลที่ใช้งานอยู่เสมอ (สร้างเมื่อ 01/10/2026 15:07)

1. ความสอดคล้องกับข้อเสนอโครงงาน

หัวข้อ §2.4.9 ของข้อเสนอโครงงาน (ทก.01) ระบุว่า SQLite ถูกนำมาใช้จัดเก็บข้อมูลสี่ประเภท แต่ละประเภทมีตารางรองรับตรงกัน

ตารางที่ 1 — ข้อมูลที่ข้อเสนอโครงงานระบุ เทียบกับตารางที่พัฒนาขึ้น
ข้อมูลที่ §2.4.9 ระบุตารางที่รองรับสิ่งที่เก็บ
ข้อมูลผู้ใช้งานusersรหัสนักศึกษา อีเมล ชื่อ รูปโปรไฟล์ สิทธิ์ และเวลาเข้าสู่ระบบ
ความคืบหน้าของนักศึกษาในแต่ละ Labprogress + activityprogress เก็บสถานะต่อ Lab, activity เก็บเวลาฝึกรายวันสำหรับกราฟ
ผลคะแนนแบบทดสอบquiz_attemptsคะแนน เต็ม และครั้งที่เท่าไรของทุกชุดคำถาม
ประวัติการโต้ตอบกับ AI Tutorai_chat_logsคำถาม คำตอบ โมเดลที่ใช้ และบริบทตอนถาม
นอกจากนี้ยังออกแบบเผื่อขอบเขตที่เหลือไว้แล้วสองจุด — คอลัมน์ course_id แยกรายวิชาปฏิบัติการฯ 1 และ 2 ออกจากกัน (ภาคเรียนที่ 2 ข้อ 1.1) และคอลัมน์ difficulty กับ hints_used รองรับระดับความยาก 3 ระดับ (ภาคเรียนที่ 2 ข้อ 1.2) โดยยังไม่เปิดใช้งานในภาคเรียนนี้

2. แผนภาพความสัมพันธ์ของข้อมูล (ER Diagram)

ตาราง users เป็นศูนย์กลาง อีกสี่ตารางอ้างถึงนักศึกษาผ่าน student_id โดยสองตารางบังคับด้วย FOREIGN KEY และอีกสองตารางเชื่อมด้วยข้อตกลงร่วมกัน

▪ Primary Key▫ Foreign Key บังคับด้วย FOREIGN KEY เชื่อมด้วย student_id แต่ไม่ได้บังคับ
เส้นทึบคือความสัมพันธ์ที่ฐานข้อมูลบังคับจริง — บันทึกคะแนนหรือบทสนทนาของรหัสนักศึกษา ที่ไม่มีในตาราง users ไม่ได้ ส่วนเส้นประคือตารางที่ใช้ student_id ร่วมกัน แต่ไม่ได้ประกาศ FOREIGN KEY ไว้ เพื่อให้ยังบันทึกความคืบหน้าได้แม้ยังไม่มีข้อมูลผู้ใช้ เช่นตอนทดสอบระบบในเครื่องพัฒนา

4. คำสั่งที่เขียนและอ่านฐานข้อมูล

ทุกคำสั่งอยู่ในไฟล์ main.py และเรียกใช้ฟังก์ชันในไฟล์ db.py ไม่มีจุดใดในระบบที่เขียน SQL ตรงจากหน้าเว็บ

ตารางที่ 7 — คำสั่ง (API endpoint) และตารางที่เกี่ยวข้อง
วิธีเส้นทางหน้าที่ตารางที่แตะ
POST/auth/googleตรวจ Google ID token + โดเมน @email.kmutnb.ac.th แล้วบันทึกลง users และออก session tokenusers
POST/progressบันทึกความคืบหน้า เขียน 2 ตารางพร้อมกันในการเรียกครั้งเดียวprogress, activity
GET/progress/{studentId}อ่านความคืบหน้าทุก Lab + เวลาฝึก 7 วันย้อนหลัง สำหรับหน้า Dashboardprogress, activity
POST/quiz-scoreบันทึกคะแนนแบบทดสอบ ทั้งตอนผ่านและไม่ผ่านquiz_attempts
POST/chatส่งคำถามไปยัง AI Tutor แล้วบันทึกบทสนทนาai_chat_logs
คำสั่งที่อ่านหรือเขียนข้อมูลของนักศึกษาต้องแนบ session token ที่ลงลายมือชื่อแล้วมาด้วย เซิร์ฟเวอร์ถอดรหัสนักศึกษาออกจาก token เองและไม่เชื่อรหัสที่หน้าเว็บส่งมา

5. เหตุผลการออกแบบ

  1. SQLite ไฟล์เดียว ไม่ใช้ ORMความสัมพันธ์ของข้อมูลเรียบง่าย ใช้โมดูล sqlite3 ที่มาพร้อม Python ได้เลย ไม่ต้องเพิ่ม dependency และตรงตามที่ระบุไว้ในข้อเสนอโครงงาน §2.7.6 ฐานข้อมูลทั้งหมดอยู่ในไฟล์เดียวชื่อ netlab.db ย้ายเครื่องหรือสำรองข้อมูลทำได้ด้วยการคัดลอกไฟล์
  2. ค่าที่เป็นการสะสมใช้วิธีบวกทับ ไม่เขียนทับwrong_count, hints_used และ time_spent_sec ถูกส่งมาเป็น "ส่วนต่าง" แล้ว backend บวกเข้ากับของเดิม เพราะนักศึกษาอาจปิดหน้าเว็บแล้วกลับมาทำต่อหลายรอบ ต้องนับรวมทุกรอบไม่ใช่แค่รอบล่าสุด ส่วน steps_done กับ total_steps เป็นค่าสัมบูรณ์ เพราะเป็นสถานะไม่ใช่การสะสม
  3. แยกตาราง activity ออกจาก progressprogress เก็บสถานะล่าสุดต่อ Lab (แถวเดิมอัปเดตทับ) ส่วน activity ต้องเก็บประวัติรายวัน (แถวใหม่ทุกวัน) เพื่อวาดกราฟย้อนหลัง 7 วัน ถ้ารวมไว้ตารางเดียวจะคำนวณกราฟยากและข้อมูลซ้ำซ้อน
  4. difficulty อยู่ใน Primary Key ไม่ใช่คอลัมน์ธรรมดาขอบเขตภาคเรียนที่ 2 ข้อ 1.2 กำหนดระดับความยาก 3 ระดับ ถ้า Primary Key ไม่มี difficulty นักศึกษาที่ทำ Lab เดิมคนละระดับจะได้คีย์ซ้ำ แถวที่สองจะเขียนทับแถวแรก ทดสอบแล้วได้ผลลัพธ์ที่ขัดแย้งกับตัวเอง คือแถวที่บอกว่าทำได้ 5 จาก 30 ขั้นตอน แต่ยังติดสถานะว่าผ่านแล้ว จึงออกแบบให้แต่ละระดับมีแถวของตัวเองตั้งแต่ต้น
  5. เวลาเก็บเป็น UTC แต่การนับวันใช้ปฏิทินไทยทุก timestamp เก็บเป็น UTC เพื่อให้เทียบกันได้ไม่สับสน แต่คอลัมน์ activity.day ใช้วันที่ตามเวลาไทย (UTC+7) เพราะถ้านับวันแบบ UTC การฝึกช่วงเที่ยงคืนถึงเจ็ดโมงเช้า ซึ่งเป็นช่วงที่นักศึกษาฝึกจริง จะไปลงแท่งของวันก่อนหน้าในกราฟ
  6. เซิร์ฟเวอร์ไม่เชื่อรหัสนักศึกษาที่หน้าเว็บส่งมาทุกการอ่านและเขียนข้อมูลของนักศึกษาต้องแนบ session token ที่เซ็นด้วย HMAC มาด้วย แล้วเซิร์ฟเวอร์ถอดรหัสนักศึกษาออกจาก token เอง ถ้าไม่ทำเช่นนี้ ใครก็ส่งคะแนนในชื่อคนอื่นได้
  7. บันทึกตอนทำขั้นตอนสำเร็จ และตอนออกจากหน้าเว็บไม่ส่งทุกการกดแป้นเพื่อไม่ให้ยิง request ถี่เกินไป แต่ดักจังหวะปิดแท็บไว้ด้วย เพื่อไม่ให้เวลาที่ฝึกไปแล้วหายถ้านักศึกษาปิดหน้าเว็บกลางคัน

6. ส่วนที่ยังไม่ได้พัฒนา

ทั้งสามรายการอยู่ในขอบเขตภาคเรียนที่ 2 และเพิ่มได้ภายหลังโดยไม่ต้องแก้ตารางที่มีอยู่

ตารางที่ 8 — ส่วนที่เหลือตามขอบเขตภาคเรียนที่ 2
สิ่งที่ยังไม่มีรองรับขอบเขตข้อใดผลกระทบ
